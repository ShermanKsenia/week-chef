# Спецификация: Agent / Orchestrator 

## Режимы / шаги
1. **INTAKE** — `parse_input` + дополнение state; если не хватает полей → вопросы пользователю.
2. **ENRICH** — загрузка calendar + inventory.
3. **PLAN_WEEK** — планирование недели: распределение свободного времени для готовки по дням.
4. **PLAN_DAYS** — по дням: цикл `get_recipes` + `generate_day_plan` до локального stop.
5. **AGGREGATE** — сбор `weekly_plan`.
6. **VALIDATE** — `validate_plan` → при fail см. retry.
7. **SHOPPING** — `build_shopping_list`.
8. **REPLY** — ответ пользователю (+ опционально propose calendar writes после confirm).
9. **REPLAN** — отдельный вход: частичное обновление плана → снова **VALIDATE** → **SHOPPING** (дельта или полный пересчёт).

## Правила переходов (упрощённо)
- Из INTAKE в ENRICH только если обязательные поля заполнены (список полей в конфиге).
- Из PLAN_DAYS в AGGREGATE после обработки всех дней недели или при явной ошибке «стоп неделя».
- Из VALIDATE в SHOPPING только при `valid=true`.
- REPLAN может вызываться из REPLY при новом сообщении пользователя с типом «сбой».

## Stop conditions
- Успех: пользователь получил план + список покупок (и опционально подтвердил календарь).
- Стоп с ошибкой: исчерпаны retries валидации/LLM, конфликт ограничений без ослабления, пустой retriever, **глобальный таймаут пайплайна** (`PIPELINE_MAX_SECONDS`).
- Стоп-диалог: пользователь просит выйти / сброс сессии.

## Retry / fallback
- **LLM parse/plan:** до **3** повторов при невалидном JSON по схеме.
- **Валидация плана:** до **3** поправок плана (новый набор рецептов / ослабление фильтра в пределах конфига).
- **Внешние API:** см. `tools.md`; после исчерпания — сообщение пользователю + отказ/возобновление спустя время.
- **Основная LLM недоступна:** переключение на **`LLM_FALLBACK_MODEL`** (см. `serving-config.md`).
- **Обе модели недоступны / квота / длительный outage:** не повторять бесконечно; ответ с кодом **`LLM_UNAVAILABLE`**; **сохранить черновик** state (`weekly_plan` partial, последний шаг) для кнопки «Повторить»; опционально **отложенная задача** на retry через очередь

## Надёжность вызовов LLM
- **Параллелизм:** не превышать `LLM_MAX_CONCURRENT` на процесс (очередь запросов к API).
- **Circuit breaker:** при серии ошибок к провайдеру — временная пауза (см. `serving-config.md`).
- Все ошибки LLM учитываются в тех же **метриках/кодах**, что и внешние tools (`observability-evals.md`, раздел LLM).

## Лимиты (PoC)
- Итерации уточняющих вопросов: **≤5** за сессию.
- Вызовы `get_recipes` на один день: **≤5** (комбинация с лимитом LLM tool-пакетов).
