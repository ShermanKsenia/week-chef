# Архитектура системы

## Описание системы
Вся система регулируется оркестратором, который выбирает из следующего списка инструментов:
* LLM tool: инструмент для анализа запроса пользователя, генерации ответов или планирования меню
* Calendar: инструмент для получения данных из календаря о свободном времени пользователя и для записи в него запланированных периодов приготовления пищи
* Recipes DB: инструмент для ретрива рецептов по заданным фильтрам
* Food DB: инструмент для получения информации о продуктах в системе (в т.ч. для нормализации ингредиентов и единиц)
* Shopping List Builder: формирование списка покупок из согласованного планировщиком набора рецептов — извлечение ингредиентов, приведение порций к числу порций из state и агрегация по продукту с итоговым количеством и единицей измерения

Для хранения состояния пользователя используется отдельная БД с памятью о предпочтениях пользователя, которая используется как state при анализе и составлении плана

## Модули и их роли
### Оркестратор
* Центральный управляющий компонент
* Управляет execution flow
* Хранит и обновляет state
* Вызывает LLM и внешние сервисы
* Принимает решения (спросить / планировать / отправить повторный запрос в БД / перепланировать фрагмент недели)
* После сборки плана вызывает валидатор; при ошибке инициирует ограниченный retry (ослабление фильтров, другие рецепты) или останавливается с объяснением
* Передаёт утверждённый набор блюд в Shopping List Builder и отдаёт пользователю план + список покупок

### LLM tool
__LLM используется для:__
1. parse_input — извлечение структурированных данных
2. generate_questions — генерация уточняющих вопросов
3. generate_week_structure — планирование недели
4. generate_day_plan — планирование дня
5. analyze_feedback — анализ пользовательского фидбека

__Парсинг ввода:__ 
Система задаёт вопросы пользователю до получения достаточного контекста

__Планирование питание осуществляется в два этапа:__
1. Генерация структуры недели: количество времени, свободного на готовку каждый день
2. Итеративная генерация по дням

__Tool-augmented planning loop__
Планнер может запрашивать дополнительные рецепты через orchestrator

### Calendar API
* Интеграция с Google Calendar
* Возвращает доступное время пользователя по дням
* Отправляет в календарь запланированные периоды приготовления пищи

### Inventory
* Хранение продуктов пользователя
* Возвращает текущие запасы
* Обновляется после каждого дня

### Recipe Service (Retrieval)
* Поиск рецептов по фильтрам
* Используется в итеративном планировании

### Shopping List Builder
* **Вход:** список выбранных рецептов от планировщика (идентификаторы рецептов + назначенные приёмы пищи), число порций из state, опционально снимок Inventory для вычитания уже имеющегося
* **Логика:** для каждого рецепта загружаются структурированные ингредиенты (из Recipes DB / кэша); количества пересчитываются под фактические порции; наименования и единицы нормализуются (словарь / Food DB); строки с одним и тем же продуктом (после нормализации) **агрегируются** в одну позицию с суммарным количеством в согласованной единице
* **Выход:** список покупок `{ позиция: продукт, количество, единица, опционально категория }` + пометки «уже есть на кухне» при вычитании запасов
* Не генерирует произвольные ингредиенты «с нуля»: состав опирается на данные рецептов; расхождения единиц решает детерминированное правило или запрос к Food DB, а не свободный текст LLM

### Plan Validator (проверка готовности плана)
* **Назначение:** детерминированная проверка того, что недельный/дневной план **можно считать готовым к показу пользователю** и исполнению, без опоры только на «смысловую оценку» со стороны LLM
* **Проверки (минимальный контур PoC):**
  * каждый слот с блюдом имеет привязанный рецепт с полным набором ингредиентов и времени приготовления из источника данных;
  * **календарная осуществимость:** для каждого приготовления длительность рецепта + буфер ≤ доступный слот в календаре на этот день/время;
  * **строгие ограничения:** аллергены и явные запреты сверяются с тегами/структурой ингредиентов рецепта; при режиме «строго» нарушение = план невалиден;
  * согласованность порций и обязательных полей state (цели, restrictions) — по заранее заданным правилам и допускам
* **Выход:** `valid | invalid` + список кодов причин; оркестратор при `invalid` запускает исправляющий шаг (повторный подбор рецептов, ослабление фильтров в пределах guardrails) или сообщает пользователю о конфликте

## Основной воркфлоу
### 1. Вход
User → API → Orchestrator

### 2. Сбор данных (диалог)
1. Orchestrator вызывает parse_input
2. Обновляет state
3. Если есть missing fields:
* вызывает generate_questions
* возвращает вопрос пользователю
* повторяет цикл
### 3. Обогащение контекста
Получение данных:
* Calendar Service
* Inventory Service
### 4. Планирование недели
LLM → generate_week_structure
→ создаётся структура недели (без конкретных рецептов)

### 5. Планирование по дням
Для каждого дня:

1. Формируются constraints (время, остатки, предпочтения)
2. Запускается итеративный цикл:
* запрашивает рецепты (get_recipes)
* LLM возвращает готовый план, когда план готов

### 6. Агрегация
* Собирается weekly_plan (дни, блюда, ссылки на рецепты, слоты готовки)
* Сохраняется черновик в state / контексте до прохождения валидации

### 7. Валидация готовности плана
1. Orchestrator передаёт weekly_plan + calendar snapshot + state в **Plan Validator**
2. При `invalid` — ограниченное число попыток исправления (другие рецепты, ослабление фильтров) или явное сообщение пользователю с причинами
3. При `valid` — переход к списку покупок и ответу

### 8. Генерация списка покупок
1. На вход **Shopping List Builder** передаются утверждённые планировщиком рецепты и порции
2. Строится агрегированный список (см. модуль выше); при необходимости вычитаются остатки из Inventory
3. Результат прикладывается к ответу пользователю и может сохраняться в state

### 9. Ответ пользователю
Orchestrator → User (план на неделю + список покупок + краткое объяснение при необходимости)

### 10. Фидбек (в том числе в конце недели)
1. Пользователь даёт фидбек
2. LLM анализирует (analyze_feedback)
3. Обновление предпочтений выполняется **с ограничениями** (см. guardrails «перекрутка персонализации»): небольшие инкрементальные изменения, потолки весов, учёт разнообразия
4. По запросу или по расписанию запускается планирование на новую неделю

## Перепланирование на ходу
Инициируется отдельным намерением пользователя или событием, не только «раз в конец недели».

### Типичные триггеры
* **Нет продукта:** ингредиент недоступен в магазине / закончился раньше срока
* **Сорвалась готовка:** не успели приготовить, отмена слота, болезнь и т.п.
* **Изменились планы:** новая встреча в календаре, укороченный вечер, отъезд
* **Отказ от блюда:** «не хочу это блюдо в этот день»
* **Обновление календаря** (webhook или повторный запрос): пересчёт осуществимости уже выданного плана

### Поток (общий)
1. Пользователь или система сообщает о типе сбоя и (по возможности) диапазон затронутых дней/приёмов пищи
2. Orchestrator читает актуальный state, **заново** при необходимости Calendar и Inventory
3. Определяется **область перепланирования:** только затронутые дни или один день, чтобы не переписывать всю неделю без нужды
4. LLM / планировщик предлагает замены рецептов или перенос слотов в рамках constraints; при необходимости — дополнительный `get_recipes`
5. **Plan Validator** прогоняет обновлённый фрагмент плана (и при необходимости стык с соседними днями)
6. **Shopping List Builder** пересчитывает список покупок **дельтой** или целиком для оставшейся части недели — в зависимости от политики PoC (минимизация изменений vs простота реализации)
7. Пользователю показывается предложение изменений; **запись в календарь** (если используется) — по политике подтверждения, как для первичного плана

### Guardrails перепланирования
* Лимит итераций и вызовов LLM на один инцидент (как в основном цикле)
* Явное предупреждение при массовом переписывании недели
* Без бесконечного автоперепланирования без участия пользователя при конфликтующих ограничениях

## Retrivial-контур
Оркестратор вызывает retrive, но может запрашиваться LLM-tool'ом по планированию

### Flow
1. Запрос на ретрив из БД выглядит так
```json
{
  "action": "get_recipes",
  "filters": {...}
}
```
2. Оркестратор получает запрос и вызывает get_recipes(filters) 
3. Результат возвращается в планирование, рецепты обязательно описываются таким образом, чтобы избежать промпт инъекций

### Tool/API интеграции
### LLM Tool
* Основной интерфейс: function-based calls
* Чёткие контракты входа/выхода
### Calendar API
* Google Calendar integration
* Возвращает availability по дням
### Recipe API / DB
Поиск по:
* времени приготовления
* ингредиентам
* ограничениям
### Inventory DB
* CRUD операций с продуктами
* Обновление после планирования

### Shopping List (API)
* Построение списка по утверждённым рецептам и порциям (вызов из оркестратора после валидации плана)
* Опционально: экспорт в текст/CSV (согласуется с политикой логов и PII)

### Plan Validator (API)
* Вход: weekly_plan (или фрагмент), calendar, state, при необходимости — нормализованные данные рецептов
* Выход: результат проверки + коды причин отклонения для метрик и retry-логики

## Failure modes, fallback, guardrails
### Failure modes
* LLM возвращает невалидный формат: не json или не фразу из заданного списка
* **Недоступность API LLM** (таймаут, 5xx, исчерпание квоты) для основной и запасной модели
* Нет подходящих рецептов
* Конфликт ограничений
* Бесконечный цикл планирования
* Недостаточно данных от пользователя
* **Превышение глобального времени** на построение плана (таймаут пайплайна)

### Fallback стратегии
* Retry LLM (ограниченное количество), затем **переключение на запасную модель** (`LLM_FALLBACK_MODEL`)
* **При полном отказе LLM:** явное сообщение пользователю (код `LLM_UNAVAILABLE`), сохранение черновика сессии, опционально отложенный retry; без «шторма» повторных вызовов (circuit breaker — см. `specs/serving-config.md`)
* Ослабление фильтров рецептов
* Использование дефолтных значений
* Прерывание с сообщением пользователю

### Guardrails
* Лимит итераций (2–3)
* Валидация ответов LLM
* Ограничение длины диалога
* Контроль обязательных полей
* Итоговое решение «план можно выдавать» принимает **Plan Validator** после структурной валидации выхода LLM

### Защита от перекрутки персонализации
* **Инкременты, а не перезапись:** изменения в профиле предпочтений после `analyze_feedback` — ограниченные по величине (например, шаги весов/скоры в фиксированных границах), без «одним фидбеком переписать всё»
* **Потолки и пол:** сильные предпочтения не могут бесконечно усиливаться; слабые — не исчезают полностью за одну сессию
* **Разнообразие:** в правилах планировщика и в state хранятся явные ограничения («не чаще N раз подряд / за неделю» для одного и того же рецепта/семейства блюд); фидбек «надоело» понижает вес, но не удаляет всё остальное меню
* **Отложенное слияние:** критичные изменения в долгосрочной памяти можно накапливать в буфере и применять пачкой после N подтверждений или по таймеру, чтобы избежать реакции на единичный удачный/неудачный день
* **Аудит:** при подозрении на узкий круг блюд оркестратор может запросить явное разнообразие или игнорировать экстремальные сдвиги предпочтений до следующего цикла
